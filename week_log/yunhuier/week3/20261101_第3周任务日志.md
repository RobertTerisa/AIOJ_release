### 1.3 一项必须先说明的取值口径（需要 owner 确认）

任务单的三条要求**在数学上不能同时成立**：

- 规模沿用“随机大”：`N = 10⁶`
- 数值范围沿用上周：元素 ∈ [1, 10⁶]
- 步长 `A[i] = A[i-1] + rand(1, 100)`，均值 50.5

按均值估算，跨度 ≈ `10⁶ × 50.5 ≈ 5.05×10⁷`，是 10⁶ 上界的 **50 倍**；严格递减版若从 10⁶ 往下减，同样会减到负数。若把值域强行钉死在 [1, 10⁶]，唯一可行的做法是步长恒为 1，序列退化成 `1..10⁶` 的排列，随机性完全消失。

本次采用的取舍：

> **保留 N = 10⁶（“随机大”的规模），把数值上界放宽到步长累加出来的自然上界（约 5.05×10⁷）。**
> 递增版从 [1, 10⁶−N] 随机取起点向上累加；递减版固定终点为 1、由总跨度反推起点，使两条序列的值域对称。

这也正是任务提示里“请使用 long long 以免 int 溢出”有意义的原因——上界已经接近 5×10⁷，虽仍在 32 位范围内，但留足余量更稳妥。

备选口径（若 owner 更希望保留 [1, 10⁶]）：把 N 降到约 `2×10⁴`，其余不变。

## 2. 本周总结

1. 递增/递减不是简单地“倒着打印”：递减版必须**先由总跨度反推起点**（起点 ≥ `lo + n − 1`），否则减到后面一定会跌破下界。两条序列因此对称——递增从下往上留空间，递减从上往下留空间。
2. 单步上限不能写死 100。若某一层剩余空间只够每步 +1，仍按 rand(1,100) 取值就会越界。实现里用 `cap = min(100, 剩余空间 − 剩余元素数)` 动态收缩，既保住随机性又不破坏上界。
3. 生成前先做一次可行性判断：严格递增 n 个整数至少需要跨度 `n−1`，不满足就直接报错退出，避免生成出“看似成功、其实越界”的数据。
4. 性能瓶颈仍是输出而非随机数：1e6 个整数约 0.15 s 稳定完成；若换回 `endl` 或保留同步流会成倍变慢。
5. 这次最值得记录的不是代码，而是**任务单本身的自洽性**：三条要求互相冲突时，按哪个优先必须有据可依、并且写下来。日志记事实与依据，PR 提请决策，两件事分开做。
